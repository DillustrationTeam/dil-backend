# Milestone add-ons

`CreatorAddons` stores optional package-scoped offers. A null PackageId makes an offer available across the creator's packages. Preset keys resolve server-side to canonical titles and stages; callers cannot change a preset's stage. Custom offers support comma-separated milestone sets (for example Sketch,Lineart) or Any. The server validates tokens and stores a canonical ordered, duplicate-free value; Any cannot be mixed with other tokens. Platform presets retain their mandatory stages. Booking attaches an extra to the first eligible stage; Workroom validates the current stage both when proposing and accepting. Prices are positive whole VND, extensions are 0–365 days. Disabling an offer does not change previously proposed or accepted snapshots.

The current rate card permits 1–10 stages with arbitrary names. Add-ons use sequence: first stage = Sketch, last stage = Final, intermediate stages = Lineart (including Base Color). A one-stage package permits Sketch/Any only. This avoids trusting editable stage titles. Existing orders without PackageId can use global offers and ad-hoc extras; new orders retain their package ID.

Public catalog: GET `/api/v1/creators/addons/presets`, GET `/api/v1/creators/{id}/addons`. Creator configuration: authenticated POST `/api/v1/creators/addons` (optional Id updates an owned offer). Package ownership is validated against the saved rate card. Creator identifiers may be profile IDs or user IDs for catalog reads.

Authenticated participants can GET `/api/v1/commissions/{id}/addons` and POST `.../addons/propose`. Creators can quote ad-hoc work; clients can propose configured offers using their server-side price and rules. The order must be InProgress and funded. A proposal snapshots price, stage, sequence, extension and title. Only the order's client can POST `.../addons/{addonId}/respond` with Action Accept/Reject.

Acceptance rechecks the exact sequence and allowed stage, even for Any proposals. Within one SQL transaction it holds wallet funds through IWalletService, records an EscrowHold ledger entry referring to CommissionAddon, increases FinalPrice, TotalPrice and EscrowHeldAmount, extends DeadlineAt and increases the current milestone's Price. Existing milestone approval therefore pays the extra to the creator. Extensions require an existing deadline. SQL Server takes an update lock on the order before reading its state to serialize concurrent decisions. Existing commission concurrency tokens and wallet rowversion protect against concurrent workflow changes. Repeating the same response is idempotent; reversing a decided response fails. Rejection only changes the proposal.

Booking accepts distinct AddonIds (max 50). Only active offers belonging to the creator/package are accepted. Their prices are snapshotted and added after license/voucher calculation; extras are not discounted or multiplied. Voucher revalidation during escrow deposit and negotiation excludes these fixed extras. Before funding, milestone base amounts are allocated to the net contract price while each stage retains its quoted extra amount, so all milestone payouts reconcile exactly to escrow. An offer's stage must exist in the package. Booking extras are accepted contract items and funded by the existing full-order escrow deposit, not charged before creator acceptance. Deadline extensions are applied when booking.

Rate-card milestones expose MaxRevisions (0–20, default 3 for existing JSON). Zero includes no revisions. Creation snapshots each configured limit into Milestone.MaxRevisions; subsequent rate-card edits do not change existing orders. Existing revision enforcement uses that snapshot. No schema migration is needed: the revision column already exists and canonical milestone sets fit the existing 20-character field.

Removed-package maintenance: SaveAsync first resolves an existing offer by creator ownership. It allows that offer to retain its original PackageId after removal from the rate card, including enable/disable, without widening scope to global. New offers and reassignment still validate against the saved rate card. Regression checks cover disable/re-enable, retained scope, and invalid new/reassigned package IDs.
